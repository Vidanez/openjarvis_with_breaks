# openjarvis_with_breaks Implementation Plan

> **For Hermes:** Execute this plan through fresh delegated work units with an independent verification after each slice.

**Goal:** Turn the `Vidanez/openjarvis_with_breaks` fork into a secure, owner-mediated personal assistant that reuses OpenJarvis while enforcing explicit trust, approval, cost, and capability boundaries.

**Architecture:** OpenJarvis remains the internal agent/runtime. A dedicated `openjarvis_with_breaks` profile becomes the policy kernel: it classifies every input by origin, admits only explicit capabilities, seals every side-effect request before owner approval, and prevents untrusted content from acquiring authority. Open WebUI remains the initial UI; the server stays loopback-only and is published later only through Cloudflare Access and a named Tunnel.

**Tech stack:** Python/OpenJarvis, pytest, Open WebUI, Cloudflare Access/Tunnel, OCI A1 VM, official Google OAuth APIs, future Meta WhatsApp Cloud API.

## External blocker resolution plan

### A. Restore OCI CLI signing authentication

**Observed evidence:** the local `DEFAULT` profile exists, its configured private key exists, and its computed public-key fingerprint matches the profile fingerprint. OCI returns `NotAuthenticated` on the first read-only API request.

**Owner-controlled procedure:**

1. In OCI Console, open **Identity & Security → Users → the same human user used when creating the OCI CLI profile → API keys**.
2. Compare the API-key fingerprint displayed there with the `fingerprint` value in the local `[DEFAULT]` profile privately; do not paste either value into chat or the repository.
3. If the matching key is absent, use **Add API key** and upload the public key generated by `oci setup config` for the existing local private key. Do not create a second local profile/key unless the current identity details are known to be wrong.
4. If the fingerprint already matches but authentication still fails, recreate the profile with `oci setup config` using the tenancy and user identity shown in the same Console user context, upload the new public key there, and retire the old key only after a successful authentication test.
5. Run this no-output authentication probe locally:

```bash
oci --profile DEFAULT --region eu-madrid-1 iam availability-domain list --all --output json >/dev/null 2>&1 \
  && echo AUTH_OK \
  || echo AUTH_FAILED
```

6. Continue only on `AUTH_OK`. Never use `--debug` in shared logs or paste raw CLI output.

### B. Resolve or classify A1 capacity

1. Run `scripts/oci-a1-capacity-report.sh` after `AUTH_OK` to inspect the exact 1 OCPU / 6 GB A1 candidate in Madrid AD-1.
2. If available, proceed only to a new final review of the saved stack; capacity reports are point-in-time and do not reserve hosts.
3. If unavailable, use a read-only report across every visible Madrid availability domain before changing any configuration.
4. If Madrid has no capacity in any domain, retain the saved stack and stop. A different shape, region, paid VM, capacity reservation, or change of resource allocation requires a separate price/capacity review and owner approval.

### C. Prove the runtime budget before provisioning

1. Select candidate model/provider profiles: local small model, approved cloud model, or hybrid fallback.
2. For every cloud provider, admit region, retention, training policy, data class, token/rate caps, and monthly cost cap before data can leave OCI.
3. Run an isolated benchmark with the selected OpenJarvis profile and Open WebUI: idle RAM, peak RAM, CPU, response latency, concurrent requests, restart recovery, and daily cost estimate.
4. Reject the A1 baseline if the benchmark cannot leave sufficient operational headroom for the OS, Tunnel, Open WebUI, OpenJarvis, logs, and backup.

### Product/security gaps in upstream

- Google OAuth asks for `gmail.modify` and Calendar write scope; Gmail paths can send/delete.
- Approvals permit reusable remembered decisions and trivial effects without mandatory owner confirmation.
- Inbound content lacks a trust boundary that blocks memory/task/action authority.
- Memory/learning lacks owner provenance and safe review/forget semantics.
- Uploads and Drive content are parsed without the required quarantine/sandbox policy.
- MCP accepts stdio commands or URLs without an admission registry.
- Baileys exists and must be excluded; only a future Meta Cloud API draft/manual path is allowed.
- OAuth tokens are JSON files under the runtime config area, not a governed runtime secret boundary.

## Invariants

1. Only an authenticated owner interaction can request a task, memory change, or external effect.
2. Email, documents, attachments, links, webhooks, WhatsApp inbound content, and model outputs are untrusted data, never instructions.
3. Every send/write/delete/schedule/change requires either a one-time owner approval tied to an immutable payload and execution receipt, or a pre-approved automation policy that is narrowly bound to the exact channel, contact, intent, response boundary, time window, and kill switch.
4. Learning may be automatic only for low-risk owner-originated preferences; it remains reviewable, expirable, and erasable.
5. Google may read and write only through explicit capability profiles. Every send, delete, calendar change, Drive mutation, or equivalent effect requires a sealed, one-time owner approval and execution receipt.
6. Attachments remain disabled until a sandboxed quarantine pipeline exists.
7. Capabilities are allowlist-based and cost/privacy governed, not permanently forbidden: providers, MCP, filesystem, and shell require separate admission profiles.
8. Baileys is permitted only in an explicitly enabled, isolated WhatsApp capability profile with owner allowlists, inbound trust classification, manual-approval and narrowly scoped automatic-reaction modes, auditable receipts, and an immediate kill switch. Meta Cloud API remains the preferred future production integration.

## Work-unit and review order

1. Slice 0 establishes criteria.
2. Slices 1–3 are the security kernel and must land before any Google/OAuth connection.
3. Slices 4–6 can be implemented only after immutable approval and trust checks are tested.
4. Slice 7 is blocked on infrastructure capacity and final runtime admission.
5. Slice 8 is discovery-only and remains after the core owner-mediated experience works.

Use one work-unit commit per slice, with targeted tests in the same commit. Before a commit, stage reviewed paths and validate the repository’s applicable pre-commit receipt/gate. Do not bypass hooks.

## Overall validation

- `pytest tests/personal_assistant -v` for new policy behavior.
- Focused existing suites named per slice.
- Full upstream test suite only after each coherent slice, not after every tiny test.
- Static configuration load test for `openjarvis_with_breaks.toml`.
- Threat-model scenario matrix: untrusted email/document/link/webhook/model output must fail to create authority.
- One independent security review focused on trust boundary and approval bypasses after Slice 3.
- Runtime smoke test only on disposable/local environment until OCI capacity and cost admission are satisfied.

## Explicitly deferred

- Automatic sends outside a narrowly scoped, owner-approved automation policy; any Google mutation without a matching receipt.
- Attachment ingestion.
- WhatsApp group monitoring by default, unrestricted/unbounded automatic replies, or any Baileys session outside its admitted owner-scoped profile.
- General shell/filesystem access.
- Broad MCP discovery or arbitrary stdio command servers.
- An OCI deployment before capacity, cost, and API authentication are demonstrably resolved.
